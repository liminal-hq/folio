## D-08 · Shared chrome and unpublished plugins are copied; published ones are dependencies

`packages/chrome` is copied from Waypoint's `packages/chrome` and the unpublished reusable plugins `window-tearoff` and `window-effects` are copied from Waypoint's `plugins/`. Each copy carries a `PROVENANCE.md` with its source repository and commit. Plugins already published to crates.io and npm (`system-appearance`, `os-prefs`, `window-manager`) are registry dependencies, never copies. When a copied package is published, the copy is deleted and replaced with a dependency.

## D-09 · Folio's own design-token names

The copied chrome used Waypoint's `--wp-*` custom properties and `data-wp-theme` attribute. In Folio they are `--folio-*` and `data-folio-theme`, and the package is `@liminal-hq/folio-chrome`. Waypoint's names appear only in `PROVENANCE.md` and in the reference prototype under `design/`. Book paper and ink are separate, never-themed tokens (`--folio-paper`, `--folio-ink`).

## D-10 · App identity

Bundle identifier `ca.liminalhq.folio`, which is also the name of the app's data and log directories. Product name Folio, publisher Liminal HQ, licence `Apache-2.0 OR MIT`.

Saved books have a separate document icon: a folded paper sheet carrying Folio's book mark. Linux packages register the format's `application/vnd.liminal.folio+zip` MIME type and install its icons in `hicolor`; Windows installers assign a multiresolution ICO to the `Folio.folio` file class. Tauri's extension association remains the source of the open command, with small installer extensions supplying the document icon. Liminal HQ's shared AppImage workflow extracts the Debian package, inheriting its MIME metadata and document icons rather than configuring an AppImage target in Tauri. A portable AppImage still needs host desktop integration before it can register file types. See `docs/file-icons.md`.

## D-11 · Settings are Rust-owned and never in browser storage

App-wide preferences (mode, theme, units, toolbar and sidebar layout, window geometry, recent books) live in a typed, versioned settings document owned by the `folio-settings` plugin, with a previous generation kept for recovery. `localStorage`, `sessionStorage` and IndexedDB are not used for app state. Per-book settings stay inside the `.folio` file.

## D-13 · Windows are created in Rust and are shadowed

`tauri.conf.json` keeps `"windows": []`. A `windows` module builds every window with `.shadow(true)`. Windows 11 draws the shadow and rounded corners; Tauri's shadow is unsupported on Linux, so the chrome draws one in CSS inside a small transparent margin.

## D-14 · Dev-only automation

`tauri-plugin-mcp-bridge` is registered only under `#[cfg(all(debug_assertions, not(windows)))]`, `withGlobalTauri` is enabled only by `tauri.conf.dev.json` (merged by `bun run tauri:dev`), and the `dev-automation` capability applies only on Linux and macOS. Release builds contain none of it.

## D-15 · Documentation site

The public documentation and manual are built with Astro Starlight and deployed to GitHub Pages, with a hand-built landing page.

## D-16 · Books are sessions in Rust, and windows are views onto them

Every open book is a `folio-session` over its `folio-package`, held by the `folio-books` plugin. A window asks for a book, sends intents, and applies the patches and events it hears; nothing but Rust changes a book. Any window can show any open book, and undo is shared per book (spec 12).

## D-17 · A new book lives in memory until it is first saved

New writes nothing. Save and Save as… ask for a place, starting at `~/Books/<Title>/<Title>.folio` (`Documents\Books` on Windows). A book never saved asks about its changes on close only once it has been touched, so starting a book and closing it again costs nothing.

## D-18 · Presets and sample pages are Rust-owned data

The six kinds, their sizes, styles and sample spreads are data in `crates/folio-presets`, written once from the design prototype and owned there since. The UI asks Rust for them and keeps no copy. `NewBookSpec` carries every field the New book wizard asks for, so the wizard window is only a screen over it.

## D-20 · Layout is Rust-owned, and the canvas draws what Rust positions

`folio-layout` shapes text (`rustybuzz`), breaks it into lines (Knuth–Plass, first-fit while typing), hyphenates (Liang patterns), pours it through frames and columns (widows and orphans, baseline grid, overset) and checks print geometry. The UI never lays text out: it asks the books plugin for `layout_spread(id, spread)` and draws the lines, with the revision the layout came from, so a stale answer is never drawn over a newer book. The four bundled families (Literata, Source Serif 4, Inter, Atkinson Hyperlegible, all OFL) are always available, so text breaks the same on every machine; installed fonts are offered as well. Dictionaries for hyphenation are embedded (en-US for Canadian English, en-GB, French).

## D-19 · The ribbon is its own package

`packages/ribbon` (`@liminal-hq/folio-ribbon`) holds the ribbon and nothing else: the chrome stays about windowing, and the ribbon knows nothing about books. Folio supplies a `RibbonModel` and handles `onCommand`. The ribbon depends one-way on the chrome for its dropdowns, so menus look and behave the same everywhere. Another Liminal app can take it without taking Folio.

## D-21 · Ruler guides belong to a spread, are stored in points, and are named by their place in its list

A guide is `{ axis, pos, locked }` on its spread, with `pos` in points like every other stored length, whatever unit the rulers show. It has no id: the intents `MoveGuide`, `LockGuide` and `RemoveGuide` name it by its index, which is safe because a guide's list changes only through those intents and each is one undo step. Rulers and guides are shown by settings (`rulers`, `marks.guides`), not by the book, so a book opens the way its reader left the rulers. A guide placed by dragging snaps to margins, frame edges and other guides, else to the unit's fine step (spec 04), and a locked guide refuses every change. Guides that belong to every page live on a master (D-22).

## D-22 · Masters belong to the person, and frames and guides are addressed by a surface

Page numbers used to be the only thing on a master, so the session rebuilt masters A and B whenever pages came, went or moved. A master is now the person's: the page-numbers setting manages only its own two frames (`fr_pn_a`, `fr_pn_b`), by box and alignment, and never deletes a master that holds anything else. A master is made when something first needs one (editing it, putting a guide on every page), and not before, so a book that never uses masters is unchanged. Editing is a separate master view on the stage (Expert), not editing in place, so a click on a page never means "change every page". Intents that name a frame or a guide take a `Surface`, either a spread or a master, instead of a bare spread, and a master edit is undone and patched through the masters the session already captures. Every-page guides are `Master.guides`, in the page's own points, named by their place in the list as D-21 says; "Put on every page" moves a spread guide onto the masters its pages use, converting x to the page's own coordinates and mirroring it for the facing master, and "Only on this spread" moves it back.

## D-23 · A page's background is a field on the page, its spread or its master, and the nearest wins

The prototype kept backgrounds in a parallel array on the spread (`bg[i]`), which drifts from `pages` whenever one moves. A background is now a field of the thing it fills: `Page.bg` for one page, `Spread.bg_span` for one background through the gutter, and `Master.bg` for every page using a master. A page shows its own, else its spread's, else its master's, else the paper. All three sit on spreads and masters, so undo, redo and patches already cover them. `Background` is one of `colour`, `gradient` (an angle and explicit stops, so a book never depends on the palette it was made with), `texture` (a bundled id, optionally tinted) or `picture` (an asset, `fill` or `fit`, and a focus). A background is part of the page, not a frame: it reaches into the bleed on the outer edge, cannot be selected or moved, and is drawn behind every frame. Rust resolves the winner (`resolve`), the canvas and the shelf thumbnails use a twin written against one shared fixture, and preflight counts a background as bleeding. The three fields are optional and left out when empty, so a book without backgrounds is unchanged and the schema stays at 1. A new book's cover colour is the cover page's own background, not a full-bleed shape.

## D-24 · Shapes are frames with their own look, and the schema stays additive until the first release

A shape is one frame, not a path: a `Shape` kind (`rect`, `round`, `ellipse`, `line`, `speech`, `thought`, `shout`) with a box, a `fill`, an optional `stroke` and `strokeWidth`, a `radius` for `round` and a `flip` for a line. There is no polygon or path model, so a shape cannot be edited point by point; each kind has a unit path the app scales to the box and draws with a non-scaling stroke, so an outline keeps its width as the frame is resized. A line is a box that may have no height or width. The note box is a `round` shape with a yellow fill. Words in a shape are fields on the shape (`content`, `style`, `overrides`), not a child frame in a group: `folio-layout` lays them into the kind's body with the `bubble` or `callout` style, so every frame operation (move, resize, lock, undo) treats shape and words as one. A frame turns about the middle of its box (`rotation` in degrees clockwise, 0–360); snapping and preflight use the upright box around the turned corners, so the one rule serves every frame type. Each is optional so an older book opens unchanged. A table is likewise one frame (`Frame::Table`): column shares, rows of cells holding inline words, a header-row count and a look, with no catch-all for unknown frame types because no book predates it. Its shape is checked when it is added (1–50 rows and columns, rectangular, positive shares adding up to 1), and layout sets each cell in the `cell` style in its own room, named `<table>#<row>.<column>`.

Until the first public release (0.1.0), the schema stayed at 1 and changes are additive: a new optional field or a new frame or shape kind is added without a migration. After it, a new kind of frame or shape bumps the schema with a migration (D-05), since a build that does not know the kind cannot open the book.

## D-26 · A section is a field on the spread that starts it, and page labels are counted from the sections

A book's page numbers change style or start again in places: Roman front matter, then Arabic from 1. A section is `{ name, numbering: arabic | roman | none, start? }` on the spread that begins it, and runs to the next spread that begins one. It is a field on the spread, not a list of indices on the book, so moving, deleting or duplicating spreads cannot leave a section pointing at the wrong place, and undo and patches (`SetSpread`) carry it with no new machinery. A duplicate does not copy the section, and the cover cannot start one. Pages before the first section are in an implied Arabic section counted from 1. Counting carries on across sections unless `start` restarts it, and a section with `numbering: none` still counts its pages. `page_labels` in `folio-model` gives every page its written number and its section's name; the canvas's `pageLabels` is its twin, and both run the cases in `labelCases.json`. The `{page}` token takes the written number, so a Roman page shows `iii`, and the new `{section}` token takes the section's name. A section's own master, so that front matter can carry different furniture, is not part of this step: masters are still given by side, and page numbers are added to any master only when the person asks.

## D-25 · Spelling is Folio's own, from a pure-Rust checker and bundled dictionaries, on by default

The webview's checker cannot give a book a spelling language: WebView2 has no setting for it, and WebKitGTK's is global and also changes `navigator.language` and the `Intl` default. Neither can check text Rust owns, such as a shape's words or a table's cells, or a run in another language. So Folio checks spelling itself. `folio-spell` is a pure-Rust crate over a small `Checker` trait, so the engine can be swapped; the first engine is `spellbook`, a Hunspell-compatible checker reading `.aff` and `.dic` files, and the first dictionary is the en-CA one from `wooorm/dictionaries`, bundled, with its SCOWL notice kept beside it. Other languages are downloaded when the person asks, each pinned by version and SHA-256 in a manifest in the repo (`crates/folio-spell/data/dictionaries.json`, fetched from the npm package through a CDN that serves its files verbatim), and each keeps its own licence beside it. A download is checked file by file and kept only whole. The catalogue holds the dictionaries under permissive or weak-copyleft licences (MIT/BSD, MPL, LGPL, CC-BY); GPL-only ones (German, Italian, Swedish) are left out until that is decided. `spellbook` is MPL-2.0, which is file-level copyleft: it is used unmodified, the licence check allows MPL-2.0 for that one crate and no other, and its notice ships in the third-party notices. The webview's own underline is turned off on the editing overlay, and the app draws underlines from ranges Rust returns, with suggestions on request. Checking is on by default (a book is words, and a misspelling in a printed book is permanent), and `spelling.enabled` in the settings document turns it off. Words the person ignores are kept per book in `proofing.ignore`, so they travel with the file and undo with it, and a personal list for every book (`spelling.personal` in the settings document) is added to and trimmed from the editor's menu and Preferences.

## D-27 · Autosave writes a recovery copy of the book beside the real file, and a crash is recovered from it

A crash or a power cut must lose seconds of work, not an afternoon. While the main window is open it asks the books plugin, at the interval Preferences sets (30 seconds by default), to write a recovery copy of each book that has changes worth keeping and has changed since its last copy. A book never saved counts once it has been touched. The copy is a whole `.folio` file under `<app data>/recovery/<id>/book.folio`, with a `recovery.json` note saying whose it is and where the real file is; it is written beside the real file and never over it, so a save that goes wrong half-way cannot damage the book, and the real file is only ever written by a save. The note is written after the copy, so a copy without one is never offered. A save, closing the book (including Don't save) and giving the copy up all take it away. A copy is therefore left only by a crash or a power cut.

The whole book is copied rather than a journal of intents because a book never saved has no file to hold a journal, because replaying intents needs ids and results that match exactly, and because the package can copy pictures it already has without reading them (the ones added since come from memory), so a copy costs the changed parts. The undo history is not kept: a recovered book starts with none.

On the next launch the start screen offers each copy, newest first, with Restore and Discard. Restore opens the book as it was, still unsaved: its real file is where it was kept so one Save puts it back, and a book never saved comes back untitled, with the changes counted as made so closing it asks. Opening a file for which a newer copy exists asks which to open. The plugin does the writing and the window decides when, so the interval and the on/off switch are settings the window reads, as the plugins never call each other. The earlier plan, an intent journal in the package's `recovery/` folder, is dropped; a package keeps ignoring a `recovery/` folder it finds in a file.

## D-28 · The styles are part of the book in memory and their own file in the package

The named styles and the typeface body text starts in used to be an untyped `styles.json` value the package held, which the session never saw: nothing could change a style, undo it, or send it to the UI as a patch, and a style could not name a typeface of its own. `Book.styles` (`look`, `fontFamily` and a table of `StyleDef`) is now part of the book the session owns, so a later intent can edit it and be undone like any other change. In the package it is still `styles.json`: a save takes `styles` out of the book it writes to `book.json` and puts it in its own file, and an open puts it back, so the format and its stable key order do not change. Keys this version does not know (colour swatches, character styles) are kept as they were. A style gains an optional `family`, which wins over the look and over `sans`; the look's typeface and `sans` still decide for a style that has none.

## D-50 · Updates are asked for, never assumed

An app that checks a server on its own is an app that tells the server it is running. Folio is local-first, and the one thing a check sends is the computer's address (the URL has no version or identifier in it), but that is still a request the person did not make. So the automatic check is off until it is turned on, in the dialog the chip opens or in Preferences → Updates, and the choice is offered once.

The release publishes `latest.json` with each installer under its bundle type (`linux-x86_64-deb`, `windows-aarch64-nsis`, …) and a signature the updater checks before anything is installed. An AppImage is repackaged from the `.deb` after Tauri has bundled it, so the program inside reports itself as a `.deb` install, and the plugin would install the download as a `.deb`. Patching the marker in the binary was considered and set aside, because where the marker sits among the other copies of the same text is a guess; the app instead notices `$APPIMAGE`, asks for the `appimage-<arch>` entry and replaces its own file (`replace_appimage`), written beside the old one and renamed over it.

A development build has no bundle type and never updates. `FOLIO_UPDATE_ENDPOINT` names a manifest of one's own, but only in a build made with the `update-endpoint-override` feature, which a release never enables.

## D-51 · The native WebView menu and browser shortcuts are off in a release build

Right-clicking a surface Folio has no menu for used to show the WebView's own menu, which looks out of place beside the in-page and native menus Folio draws itself. `tauri-plugin-prevent-default` is registered once in the composition root, so every webview gets it and no component needs its own `contextmenu` handler. A release build blocks the WebView context menu, devtools and the reload, find, print and open shortcuts; a debug build keeps the menu, devtools and reload. `Shift`+`Tab` is left out of the blocked set, because blocking it would stop reverse keyboard focus navigation. Folio's own menus still open from the pointer and from `Shift`+`F10` or the Context Menu key, since the plugin only cancels the browser's default action.

## D-52 · A book opened from the file manager reaches the running Folio, and opens like File → Open

The `.folio` file association starts `folio <path>`, and nothing read that argument, so Folio opened on the start page. The `tauri-plugin-single-instance` plugin is registered first, so a second launch hands its arguments to the running app and exits; a cold start reads its own arguments in `setup`. Both queue the paths in `open_files::PendingOpens`, and the main window takes them with the `take_open_files` command on mount and again whenever `folio://open-files` is sent, so a path that arrives before the page has loaded is not lost.

The paths are opened in the main window through the File → Open runner rather than straight from Rust. That keeps one way to open a book: the save-changes question for the book being shown, the crash-recovery choice and the open-twice check all apply, and a failure can be told to the person in a message dialog, since the start screen's own notice is not on screen when a book is showing. The cost is that opening needs the webview to be running, which the main window always is. Relative paths are read from the second launch's working directory, and the `file://` addresses the Linux desktop entry passes (`%U`) are decoded.

## D-49, amended · The ribbon's Tools tab opens one tool

D-49 had the Book tools window open on one of four areas, chosen from the app menu or the Tools menu. Every built tool is now also a button on the ribbon's Tools tab, so `open_book_tools` takes an optional `tool`: a tool's id such as `structure.contents`, whose first part names its area. The tool decides the area, and a tool id that is not one of an area's is dropped, leaving the area alone. The window remembers the request (`ToolsAsked`) for a window built after it was asked, and sends it as the event payload when it is open. The app menu and the Tools menu still open areas. One command per tool (`tool.copyright` … `tool.royalty`) is what the buttons run, so a menu entry per tool can use the same commands later.

Find & replace has no behaviour yet, so its button on the Tools tab is listed and unavailable, like the Home tab's. Spelling on the Tools tab is the same switch as Home's.

## Clipboard · Page objects are copied as Folio JSON and pasted as new frames

Nothing handled copy, cut or paste for page objects, so Ctrl+C reached the webview as an unhandled native copy. Copy now puts the selected frames in memory and, as far as the webview allows, on the system clipboard as `application/x-folio-frames+json` (a `{ folio: 1, frames }` payload) and as plain words: the words of text frames, else the frames' descriptions, else "Folio: n frames". The words are what other programs get, and what a paste compares the clipboard's with to know it still holds the last copy and not something copied elsewhere since; when the system would not take the copy, an empty clipboard is the only sign. Ctrl+C and Ctrl+X are handled on the keydown (the target is not an editable field, no dialog is open and no words are selected on the page), and paste is handled on the `paste` event, which is also where a picture on the clipboard arrives.

A paste is one `AddFrame` per frame with new ids (a group's children too), the 12 pt offset and the rules of `DuplicateFrame`: the copy is not locked, not from a master, and not another slot in a story's flow. Each paste of the same copy nudges a further 12 pt; the page menu's Paste centres the frames on the click. Cut copies every selected frame and deletes only the free ones. Frames are separate undo steps, as for a duplicate of several.

Paste special has three further ways. **Paste text only** puts the words of the clipboard, or of the frames copied, in a new text box; Ctrl+Shift+V does it, taking the words from the paste event and, if the webview sends none, from the clipboard 150 ms after the key. **Paste into frame** is offered for one free text box, shape or picture frame: words replace its words and a picture replaces its picture. **Paste in place** puts the frames where they were. A frame is not pasted as a picture, since that needs the frames drawn to an image.

## Groups hold frames in page coordinates

`Frame::Group { children }` existed in the model with nothing behind it. `GroupFrames` wraps two or more free frames of a spread, and `UngroupFrames` takes a group apart. A group's children keep boxes in the page's coordinates, not relative to the group: layout, preflight and export open a group out into its frames (`folio_model::leaves`) and so draw nothing differently, and a frame's id and the flows, edits and undo that find frames by id still find a frame inside a group. The cost is that moving or resizing a group has to move its children, which `Frame::set_rect` does (translate, then scale each box by how much the group's box grew), as does a duplicate or a paste. The group's box is the box that holds its frames as they are turned. A group is not turned, since turning would need a transform every consumer applies; take it apart to turn the frames. Groups are made only on spreads, not on a master page, so the master code that places items on each page need not know of them; a frame that carries a story from frame to frame is not grouped.

## The ribbon fits the window and never scrolls

The ribbon's panel scrolled sideways when a tab was wider than the window. It now fits: a `ResizeObserver` notes the panel's width, and before each paint the groups give way from the right (icons only, then folded into one button that drops the group down, then under More) until the panel is no wider than the window. The fit is worked out again from the whole groups when the width, the tab, the mode or the density changes, so widening the window brings the groups back.

## D-53 · Every edit to words is one `EditText` intent, by code points of a paragraph

The page used to edit words in a `<textarea>` and send the whole text back (`SetText`, `SetParagraphText`), and Rust guessed what had changed by comparing the common prefix and suffix of the old and new text (`retext`). That guess is why typing in the middle of repeated words can pick up the wrong run's look, and why a plain box can show only the look of the first run. The new editor sends what it did instead: `EditText { target, from, to, insert, look, step }`. The editor is a hidden input that takes the keystrokes and a caret and selection drawn over the page's own lines, so the page and the editor wrap identically; the words stay in Rust (D-02) and every mutation is still an intent.

A place in words is `TextPos { para, offset }`: the paragraph and the Unicode code point in it. That is what `StyleRange` and the page's selection code already count. Bytes stay in Rust and UTF-16 stays in `apps/folio/src/text/units.ts`; the layout sends the code point range of every line and a stop for every code point of every run, so the page never converts. Targets are a text frame's own words, a shape's, one table cell's, or a flow's story. A frame's own words are paragraphs split at the line break, and an empty paragraph keeps a zero-length run with its look, written back as a line break at the start of that run, so emptying a paragraph and typing again does not fall back to the style's font.

What is typed takes the look of the words before it (the first words' look at the very start), changed by the edit's `look`, which is how a bold or font set with nothing selected reaches the next characters. A paste with formatting sends paragraphs with their own runs and styles. A keystroke is `step: typing` and joins the previous typing step when it came less than a second before and began where that one ended (or, for Backspace, ends where it ended); a caret that jumped, Enter, a paste, a cut, a spelling fix and a change of look are steps of their own. The old text intents stay for the story editor, the MCP server and the tools until nothing but those uses them.

An edit is refused whole, changing nothing, when a place is outside the words, the range ends before it begins, a colour is not a swatch or `#rrggbb`, or the frame is locked, from a master, or flowed (a flowed frame is edited through its story).

Measured before the editor was built (the dev profile at optimisation level 3, one core, no IPC, the bundled fonts): a keystroke into a 300-word frame costs 0.02 ms to apply the intent, 3.6 ms (p50) and 4.3 ms (p95) to lay out the spread and 0.01 ms to serialise it (a 3.9 KB layout), so it fits well inside a frame. A keystroke into a story of 400 paragraphs of 150 words does not: laying the flow out again takes 1.1 s (p50) to 2.3 s (p95) for the spread, and the page-count check that runs after every story edit (`frames_needed` and `frames_used`) another 4.6 s (p50), because both lay out the whole flow from the top. A story edit therefore needs a per-paragraph layout cache (only the edited paragraph is shaped and broken again, the rest placed from the cache) and the page-count check must not run on every keystroke; the cache is built in its own layer before linked frames are edited in place.

The per-paragraph layout cache (`ParagraphCache`) took a 400-paragraph story laid out spread by spread from 1.5 s to 0.31 s in an unoptimised test build once one paragraph had changed, the rest being placing the cached lines. The page-count check that follows a story edit still lays the flow out from the top with more frames; with the cache it takes the same paragraphs as hits, but it is still the next thing to make incremental (or to run only when a paragraph's line count changed) before a very long story is edited in place.

## D-54 · The on-page editor is the default, and the text box stays for a release as a fallback

Once the on-page editor (D-53) could edit a frame, a shape, a table cell and a story, with the page's own wrapping, ranges styled from the ribbon, spelling underlines and a menu, one undo step at a time with the caret put back, it did what the text box did and more, so `editing.newEditor` starts on. The text box, the story box and their code are not deleted yet: the editor is a new way to take input (an invisible input at the caret, an input method that has only been tried through test events), and a person whose input method or screen reader misbehaves with it can turn it off in Preferences → Editing and carry on. Removing `TextEditor`, the story box and the setting is the next step once it has been used on real input methods on WebKitGTK and WebView2, and is a deletion with no new behaviour.

## D-57 · Smart punctuation is on by default, set by language, and put back with Backspace

Straight quotes, `--` and `...` are typewriter habits that every book wants set properly, and a person who has never heard of an em dash should get one without asking, so `editing.smartPunctuation` starts on (a personal setting like spelling, not stored in the book). The rules live once, in `folio_model::smarten` (`crates/folio-model/src/smart.rs`), and typing, paste, import and the Book tool all use them: a quote opens at a paragraph's start or after a space, an opening bracket, a dash or another opening quote and closes otherwise; an apostrophe closes inside words and before digits (’90s); `--` is an em dash (a third hyphen joins it), a hyphen between spaces an en dash, and three dots one ellipsis. Quote marks follow the language: English (and anything without a rule of its own) “ ” ‘ ’, French and French (Canada) « » with non-breaking spaces inside and ‘ ’ for a quote within one, German „ “ ‚ ’ (the apostrophe is ’, so a German single quote closes with ’ too). The language is the book's (`book.language`) because runs have no language of their own yet; it moves to the run when per-run `lang` lands.

As you type the rules see only what is before the place, so a rule can rewrite the end of it: the second hyphen turns the first into the dash and the third dot turns two into the ellipsis. `smarten(before, inserted, style)` therefore answers with the words that replace the last `rewind` characters of `before` together with the inserted words, and `edit_text` applies that as one `EditText` that begins `rewind` characters earlier, so it is one undo step and the page never shows a hyphen that is about to change. Rust does it (`EditRequest.smart`), not a copy of the rules in TypeScript: the round trip is the one a keystroke already makes (`edit_text` is a single call that lays the spread out again, measured at about 4 ms in D-53), so a second implementation to keep in step was not worth the saving. The answer says what was set and what was typed (`SmartNote`); Backspace straight after a conversion, with the caret still at its end, sends one more `EditText` that puts the typed characters back, and the next characters are left as typed so that a reverted `--` is not made a dash by the next hyphen. Plain text pasted (Insert::Text) is set in the same call; text pasted with Folio's own formatting, Enter, deletions and a finished input-method composition are not touched. A quote typed before a number reads as opening until the digit arrives, and the digit then turns it into an apostrophe.

Importing sets the words by the same rules: Word, OpenDocument and Rich Text paragraphs run by run (a rule can reach back into the run before and keeps each run's look), and Markdown in place of pulldown-cmark's own smart punctuation, which made `--` an en dash and so disagreed with typing; `code` spans are left as written. The import follows the setting. The Book tool uses the book's language too and now covers table cells.

## D-58 · A paragraph has its own look, and space before and after add together

The user wants space between paragraphs they can set, and a sentence that follows a line break to be able to differ from the one before it, as each character already can. So spacing, line spacing, indents and alignment belong to the paragraph, not the frame: `ParaLook` (all optional; points, with line spacing a multiple of the size) is held on `StoryPara.look` for a story and on a `looks` list beside `inline` for the words of a frame, shape or cell, and `SetParagraphLook { target, from, to, change }` changes the paragraphs `from..=to` of a `TextTarget` (one undo step; repeats on the same range merge). Values are validated in Rust (lengths 0 to 720 pt, line spacing 0.5 to 5), and a field a paragraph leaves out takes its style's, so no preset gets a default gap and older books open unchanged.

Space before and space after **add** (Word and LibreOffice do the same, and `folio-layout` already did), and space before is dropped at the top of a column. CSS margins collapse to the larger, so the EPUB writes a paragraph's own spacing as padding (with the margin on that side set to nothing); the spacing a style gives in the stylesheet is margin and still collapses, which is the one place the file and the page can differ.

Enter copies the look to the new paragraph (as a word processor does), joining keeps the first paragraph's, and an edit leaves the looks of the paragraphs it did not touch. The ribbon's paragraph controls and the Properties panel's **Paragraph** section act on the paragraphs under the caret or selection of the open editor and, with no editor open, on every paragraph of the selected frame, in Easy as well as Expert. Bullets, numbers, drop cap and letter spacing stay unavailable: they need a list model, a drop-cap model and tracking per range.

## D-59 · Words in a story or a cell are styled by `StyleText`, and the ribbon shows what every selected character has

`StyleRange` counts characters of one frame's words and `StyleStoryRange` one paragraph of one story, so neither could style a stretch of a table cell, and a stretch that crossed a paragraph of a story would have been several intents and several undo steps. `StyleText { target, from, to, change }` takes a `TextTarget` and two `TextPos` places, as `EditText` does, styles the end of the first paragraph, the whole of those between and the start of the last, and is one undo step, so any words can be styled the same way. `StyleRange` stays for a frame's or a shape's own words (it needs no paragraph arithmetic) and `StyleStoryRange` stays for the MCP server; the ribbon sends `StyleText` only for the words of a story or a cell. It refuses an empty stretch, a place outside the words, an empty change and a colour that is neither `#rrggbb` nor a swatch, and a locked frame, changing nothing, and a change to a story is checked for the pages it now needs like any other story edit.

The editor tells the ribbon where its caret and selection are (`textSelection.ts`), by character count for a frame and a shape, and by `target`, `from` and `to` (a caret by `target` and `pos`) for a story and a cell. The ribbon reads the look of those words from the book it already has, and shows bold or italic pressed only when every selected character has it (so the next press makes all of them so rather than all of them plain), and the font only when the whole stretch shares one (the style's font is the empty name, and mixed fonts show none). With the caret alone it shows the look the next typed character would take, or the pending look when one is set. This replaces the ribbon showing the first frame's overrides whatever was selected. The selection, caret and pending look are one value that changes when any of them does, which is why the Home tab follows the caret.

A font chosen with the caret alone in the words is a pending look like bold, italic and colour: it goes with the first words typed after it as the edit's `look` (a step of its own), moving the caret forgets it, and an installed font is kept with the book when it is chosen, as when it is chosen for a selection. The Font list shows the pending font until then.

## D-60 · The caret crosses the frames of a story on one spread as if they were one column

A story runs through linked frames, and editing it from one frame stopped the caret at that frame's last line. The layout already gives every line of every frame its paragraph and code point range, so the editor needs no new data: `flowGeometry` places the lines of the story's frames on the spread on one plane (the edited frame's coordinates, each frame moved by where it sits) and the existing caret, selection and vertical-movement code runs over that plane unchanged. What changes is how a point is turned into a place and how a column is kept. A click or drag is first given to the frame nearest to the point (by its box) and then to the line there, because two frames side by side on a spread have lines at the same height, which a search by height alone cannot tell apart; and up and down measure the column from the left edge of the frame the line is in, so a caret one letter into the last line of the left page goes one letter into the first line of the right page, not to the same distance from the edge of the first. The other frames get an invisible, pointer-taking area over their box so a click or a drag can start or end there.

It stays on one spread because the layout is made a spread at a time: lines of frames on other spreads are not in the layout the editor has, and asking for them would be a request for every spread and a surface that spans pages. Selecting across spreads is left to the follow-up (P9). A story with a turned frame on the spread also falls back to one frame, since a turned frame's lines do not sit on the plane of the others. Frames of a story that are on a master are not part of it.

## D-61 · The page-count check after a story edit is one pass that keeps no lines, and the story's runs are not re-checked for missing characters

D-53 measured a keystroke into a story of 400 paragraphs of 150 words at 1.1 s (p50) to lay out the spread and 4.6 s for the page-count check (`frames_needed` and `frames_used`), because both laid the flow out from the top, and the per-paragraph cache (R1) took the shaping out of that. Measured again here (the dev profile at optimisation level 3, one core, no IPC, the bundled fonts, 400 paragraphs and 68,800 words, one paragraph changed between runs, `crates/folio-layout/tests/long_story.rs` with `--ignored --nocapture`), what was left was not shaping. After R1: the spread took 11 ms and the check 46 ms when the story had more words than frames (the usual state while the first pages are being added) and 52 ms when it fitted, which is two passes of about 26 ms: about 9.5 ms building the story (every run's font checked, character by character, for glyphs it lacks, in `split_with_fallback`), under 1 ms placing cached paragraphs, and the remaining 15 ms copying every placed line and describing every run for the wire, both only to be thrown away.

Three changes, none of which changes an answer. The check is one call, `Layouter::page_fit`, which pours the story once and answers `needed` and `used` together (`frames_needed` and `frames_used` remain, as wrappers). The pour used for it, `flow_extent`, places every line as `flow` does but keeps none, and `Flowed.frames_reached` carries what the lines would have said. And `ParagraphCache` remembers the runs whose font covers every character they hold (keyed by the words, family, weight and italic; cleared with the cache when the fonts change, as the paragraphs are), so a keystroke no longer scans 400 KB of text for missing glyphs. A paragraph from its start is also no longer copied before it is looked up. Measured after: the spread 0.8 ms; the check 3.4 ms when the story needs more frames and 2.6 ms when it fits, so a keystroke into this story costs about 6 ms of layout where it cost about 60 ms, inside the 16 ms of a frame. Opening such a story, or changing the fonts, still shapes all 68,800 words once (about 0.8 s here); nothing in this layer changes that. The per-paragraph step stays a pass over the whole story (arithmetic over cached lines, 0.3 ms here) rather than a stored column state per paragraph: the pass is no longer the cost, and a stored state would have to be invalidated by every change that moves a column.

## D-62 · Find and replace is a search in Rust over every place words live, and replace is a batch of `EditText`s

The words of a book are in Rust (D-02), so the search is too: `folio_engine::find` is a pure function of the book, and the page only shows its answer. It reads the same places `EditText` can reach (D-53): every flow's story, a text frame's own words, a shape's, each table cell's (groups included) and the frames of the master pages. It does not reuse `tools.rs::sources()`, which has no spread, no locked flag, no master pages and no group children, all of which a match needs; it walks the frames with the same cases instead.

A match is `{ target, para, from, to, spread, master, context, locked }`: `target` is the `TextTarget` and `para`, `from` and `to` the paragraph and the Unicode code points in it, exactly what an `EditText` takes (so a match can be sent back as an edit and the page never converts units, D-53). Matches are in reading order: by spread, then page of the spread, then the frame's place on the page (top to bottom, left to right), then the words' place in the frame; the words of a master page come last and belong to no spread. A story has no one place, so `Books::find` asks the layout where its words are: it lays out only the spreads that hold a frame of a story that has matches and puts each match on the spread and frame of the line that holds it.

Options are match case, whole word and a regular expression. Case is folded the way Unicode does it, not only for ASCII. Whole word is a boundary of letters, digits and `_`, with an apostrophe between letters inside the word ("don" is not found in "don't"), and a query that starts or ends with punctuation needs no word edge there; a rejected stretch is searched again from its next character so a later match inside it is not lost. Matches do not overlap, and an empty match (`x*`) is no match. The `regex` crate is the engine because it runs in time linear in the words searched, so a pattern like `(a+)+$` cannot hang the app; what remains is a pattern that is large, so a query is limited to 1 000 characters and a compiled pattern to 1 MiB, and a pattern that does not parse or is too large is refused with a message and finds nothing. A search stops at 10 000 matches and says so (`truncated`). Regular expressions are an Expert option; Easy has the box only.

Replace is `Books::replace(ReplaceRequest { find, replacement, only, master })` and makes `EditText` intents in one batch (`apply_batch_by`), the same way the Book tools' fixes are one undo step. Each match is two edits: the new words are inserted at the end of the old ones and the old words are then taken out, so the replacement takes the look of the words it replaces through the existing rule that typed words take the look of the words before them, with no new look logic. The words are put in as written, with no smart punctuation (the person asked for exactly these words; D-57 is for what is typed). In regex mode `$1` and `${name}` in the replacement are capture groups and `$$` a dollar sign; in a literal search the replacement is literal. Edits are made last place first so a replacement holding a line break does not move the places before it. `only` names one match as `find` reported it; if it is no longer there, nothing is replaced.

Words that are not to be changed are skipped and counted, not refused: a match in a locked frame (a story is locked only when every frame of it is), and a match on a master page other than the one being edited (the book's window passes the master it is editing, if any; masters are shown to everyone but changed only on purpose). `ReplaceReport { replaced, skippedLocked, skippedMasters }` is shown by the bar ("Replaced 12. Left alone: 3 in locked frames or on other master pages."). A frame that came from a master (`fromMaster`) counts as locked, as `EditText` refuses it.

The page shows what was found with the lines the layout already sends: `selectionRects` gives a box for each line a match touches, drawn in `--folio-accent` (the current match stronger), in every frame of the spread that shows the words, including a locked frame. Going to a match opens the spread (or the master page) and, for words that can be edited, the on-page editor on the frame, shape, cell or story frame that shows them, with the match as its selection. The bar keeps the keyboard while that happens: `TextSurface` takes a `reveal` selection without focusing its input, and its blur does not close the editor when the focus goes to the find bar (as it already does not for the ribbon). Esc closes the bar and puts the focus in the editor if one is open, else on the page. Ctrl+F and Ctrl+H are menu commands (`edit.find`, `edit.replace`) that ask the book's window for the bar, like Export; the key is left alone in any text field except the on-page editor's input, so the find bar, the inspector and Preferences keep their own Ctrl+F.

Not built: a shortcut on the Tools tab (it lives in the ribbon stack that has not merged); filling the query from the selected words; replacing within the selection only; find across several books.

## D-63 · Underline and strike are run properties, drawn as rules whose place and thickness come from the font

`Run` has two flags, `underline` and `strike`, and `RunChange` two optional ones, so `StyleRange` and `StyleText` set and take them away like bold. Both default to false and are left out of the saved book when false, so books written before open unchanged and a book that uses neither is byte-for-byte as before. Runs that differ in either are not joined (`alike`), and words typed inside a stretch take its look through the existing rule (D-59), including a pending look at the caret.

Layout, not the page, decides where the line goes, so the page and the exporters agree. Each `LayoutRun` carries `underline` and `strike` as a `Stroke { offset, thickness, width }` in points: `offset` is from the baseline to the middle of the rule (positive downwards), taken from the font's `post` (underline) and `OS/2` (strike-through) tables through `ttf-parser`, with a thickness of at least a fiftieth of an em and the usual one-tenth and three-tenths of an em where a font has no table. The tables give the top of the line above the baseline, and the middle is what a page draws about. A run is laid out one word at a time with the spaces between as glue, so `width` runs on over the space to the next run on the line when that run has the same rule, and stops at the word's end otherwise: an underlined phrase is one line, two underlined words with a plain one between them are two.

The page draws a `<rect>` in the words' colour. The PDF draws the same rectangle after the glyphs, with the words' fill. The fixed-layout EPUB writes `text-decoration: underline line-through` on the span (the spaces between words are inside the span, so the line is continuous), and the reflowable EPUB writes `<u>` and `<s>`. The Word, OpenDocument and Rich Text importers read underline (`w:u` other than `none`; `text-underline-style` other than `none`; `\ul` and its variants until `\ulnone`) and strike (`w:strike`/`w:dstrike`; `text-line-through-style`; `\strike`). Markdown has neither, and the clipboard's HTML writes `<u>` and `<s>`.

The ribbon's Underline and Strikethrough follow Bold: pressed only when every selected character has them, and a frame selected with no editor open has them put on all its words, or taken off when they are all set. Ctrl+B, Ctrl+I and Ctrl+U in the on-page editor press the ribbon controls (Expert only, as the controls are); they were listed in the spec for the text box but the on-page editor had no keys for them.

Not built: a distinct double underline or wavy line, a colour or offset for the line of its own, skipping the descenders of letters, and small caps, super and subscript and highlight, which are separate steps.

## D-64 · A run may have its own size and letter spacing, and a line is as tall as its tallest run

`Run.size` (points) and `Run.tracking` (thousandths of an em, so a whole number and no rounding in a saved book) are optional and win over the style's, as `font` and `colour` do; a run with neither is saved as before. `RunChange` sets them and has `clearSize` and `clearTracking` to take the override away, because a tracking of 0 is a value (no spacing at all, whatever the style says) and cannot also mean "none". Rust holds them to 1–1000 pt and −500–2000 thousandths, and a size that is not a number is ignored. Runs that differ in either are kept apart, and typed words take the look before them as for every other property.

Layout needed no new rule for mixed sizes: each span's ascent, descent and `size × line height` are taken by the maximum over the line (`paragraph.rs`), and the baseline is placed at the line's tallest ascent plus half its leading, so a line with one large word is taller and its small words sit on the same baseline. The paragraph cache already hashed size and tracking. The reflowable EPUB writes `font-size` in ems of the paragraph's own size (a chapter title is an `<h1>`, which a reader sets at twice the body text) and `letter-spacing` in ems; the PDF and fixed-layout EPUB take both from the laid-out runs as they did.

The Size box and the Letter spacing menu act on the selected words and, at a caret alone, on the words typed next (the pending look); with no editor open they act on all of a selected frame's words (Size is still the frame's `OverrideStyle`, as it was; Letter spacing, which a frame never had, is a `StyleRange` over the whole of its words). The size of a run is its own, else the one its style names, else the frame's, and the box shows the first selected character's with a dash and an accessible "mixed" when the characters differ (the stepper steps from the first one's size). The menu offers Tight (−20), Normal (0), Loose (30), Very loose (80) and "The style's", and ticks a choice only when every selected character has it.

The Word, OpenDocument and Rich Text importers read a size (`w:sz`, `fo:font-size`, `\fs`) and a letter spacing (`w:spacing`, `fo:letter-spacing`, `\expndtw`, turned into ems of the run's size, or of 11 pt when it names none). Those files name the body size on nearly every run, and keeping it would pin each run over the Folio style its paragraph is given, so the size most of the words share is taken away and only the runs that differ from it (a larger word, a smaller note) keep theirs.

Not built: sizes in relative units, a baseline shift (super and subscript), and a per-run line height.

## D-65 · A run may be in another language, and the language reaches spelling, hyphenation, quotes and the exports

`Run.lang` is an optional BCP 47 tag (`fr-CA`), over the book's language, and `RunChange.lang` sets it (an empty tag takes it away; a tag that is not shaped like one, or names no language such as `zxx`, is ignored, and a good one is written in its usual case through `clean_lang`). Runs in different languages are not joined, and words typed inside a stretch take its language like every other property. A run with no `lang` is in the book's language, so a book that uses none is saved as before.

Layout gives the span the language (`TextStyle.lang`) and each use reads it from the span: shaping passes it to the font's features, and a word is hyphenated by the language of the span its first letter is in (a word split across two languages is treated as the first's, which is the rare case worth neither a split nor a rule). The paragraph cache key includes it. `LayoutRun.lang` carries it to the page and the exporters. The layout's `Proofer` is now `Fn(&str, Option<&str>)`: a paragraph is checked in one stretch for each run of neighbouring spans in the same language, and the engine looks up the dictionary for that language once per layout. A language with no dictionary is not checked, rather than checked against the book's, because every word of a French phrase would be a misspelling in the English dictionary. The proofing list (`spell_check_book`) does the same, and offers no replacement for words with a language of their own, because a replacement made of plain words would lose it.

Smart punctuation takes the quote style from the language of the words typed into: the language chosen for the next words (`look.lang`), else the run before the place, else the book's. The Book tool sets a paragraph, cell or text box by the language every run of it shares and by the book's otherwise (it replaces the words of a paragraph whole, so a paragraph of mixed languages is not split by run). Folio's importers do not pass a language, so imported words are set by the book's.

The ribbon's Language list (Home → Editing, Expert) is the Language list of the Properties card, with the book's language first ("Book's language" takes the run's away) and shows the choice for the selection's language (`fr-CA` is the French choice; a language with no choice is added as itself; words in several languages show "Mixed languages", which does nothing). It acts on the selection, on the words typed next at a caret, or on all of a selected frame's words. The proofing group's own list still sets the book's.

The reflowable and fixed-layout EPUB write `lang` and `xml:lang` on a span around the words. The PDF is not tagged, so it carries the book's language in its metadata and no more: a language for a run needs the tagged structure the PDF export does not write. The Word, OpenDocument and Rich Text importers read `w:lang`, `fo:language` with `fo:country`, and `\langN` (for the languages Folio has a dictionary or rules for), and drop the language most of the words share, as sizes are (D-64), so that a document written in the book's language does not mark every run.

Not built: a language per run in the PDF, and a dictionary offered for download when words are in a language Folio has none installed for.

## D-66 · A link is an address on a run, drawn by the page, and only addresses Folio can follow safely are kept

`Run.href` is an optional address, set by `RunChange.href` (an empty one takes the link away). `clean_href` in `folio-model` keeps `http`, `https`, `mailto` and `tel` addresses with something after the scheme, and `#spread-n` (a spread counted from 1, the cover included); everything else — `javascript:`, `file:`, `data:`, an address with a space or a control character — is refused, so a book that arrives from elsewhere cannot carry one the app would then follow. A link joins the words beside it only when it goes to the same place (`alike`), and words typed at the end of a link do not go on linking while words typed inside it do (`replace_range`). Old books open unchanged: `href` is left out of the saved book when there is none.

A link is not part of a run's look. Layout sends `LayoutRun.href` and `LayoutRun.link`, a rule at the font's underline position that runs on only into the same link; the page draws the words and the rule in the link colour (the Navy of the text colours, `#2b3a67`, since paper is never themed) unless the run has a colour of its own. The exporters read `href` and draw no rule of their own, so what a link looks like in print is the book's choice, not the link's.

The address is chosen in a small dialog opened by Ctrl+K in the on-page editor, in Easy as well as Expert, or by the Home tab's Link control (Expert, as the spec has always said for links). The dialog makes an address of what a person would type (`example.org`, `me@example.org`) so no one has to know about schemes, offers a page of the book from a list, and says why it refused an address. The check is written twice, in `clean_href` and in `checkHref` (`apps/folio/src/text/links.ts`), and the model's has the last word. The dialog works on the words as they were when it opened, so it does not matter that opening it ends the editing.

Ctrl+click (Command on a Mac) follows a link, on the page and in the editor; a right click on a link in the editor offers Follow link, Edit link… and Remove link. A web, email or phone address is opened by `tauri-plugin-opener` — a registry dependency, as the project's plugin rules say — with only `allow-open-url` and the default web, mail and phone scope granted to the main window, never `reveal-item-in-dir`. A `#spread-n` link shows that spread.

Not built: a link to a place that is not a spread (a chapter, a heading), a link on a picture or a frame, a pending link at a caret, and links in the old text box.

## D-67 · Links are written to every file that can carry one, left out of print files, and checked by preflight

The reflowable EPUB writes `<a href>` round linked words. The book is a story there, not pages, so a link to a spread (`#spread-n`) needs an anchor: the exporter writes an empty `<span id="spread-n"/>` where each spread begins in the story (in the chapter that opens at or after that point, so a spread that starts with a chapter title is anchored in that chapter), and once every chapter is written it points each link at `chapter-NNN.xhtml#spread-n`, or at `#spread-n` within its own file. The cover has no words, so a link to it lands at the start of the story. A link to a spread the book does not have goes to the first chapter, so a file never has a link to nowhere (preflight tells the author). The fixed-layout EPUB wraps the words of a line in `<a>` and points a link to a spread at the page file it begins on.

The Sharing PDF carries a link annotation (zero-width border, so nothing is drawn round it) over each stretch of a line whose words link to the same place, with the corners turned with the frame; an address is a `/URI` action and a spread a `/Dest` on its first page, left out when that page is not in the file. The print targets (KDP paperback and hardcover, the print shop's PDF/X, the cover) carry none: the spec has always said a KDP interior has no annotations, a printed link does nothing, and PDF/X restricts annotations. Whether KDP would accept links in an interior is not claimed (⚠ to verify). The link colour and rule that the page draws are not exported, so the exporters stay faithful to the run's own look.

The three importers that can read links (Word, OpenDocument, Rich Text) and the Markdown importer keep an address the model accepts (`clean_href`) and keep only the words of one it refuses or of a link to a place in the document, with one note in the report. The reader preview turns every `<a href>` into `<a data-href>` so a click cannot take the preview page off to the address.

Preflight adds `LinkInvalid` (an address the model refuses, which can only come from a hand-edited or damaged file or an older build, a warning), `LinkNowhere` (a `#spread-n` past the end of the book, a warning, since a spread can be removed after the link is made) and `LinkEmpty` (a link with only spaces to click, a note), each said once for an address on a frame, with the address in the item. A story is checked at the first frame of its flow.

Not built: a link to a heading or chapter by name, bookmarks in the PDF, tagged-PDF link structure (the PDF is not tagged), and a link followed in the reader preview.

## D-68 · HTML from the clipboard is read in Rust by a small reader of its own, and only what a run can hold comes through

`folio-import::import_html` reads pasted `text/html` into `StoryPara`s of `Run`s, and the books plugin offers it as `paste_html(id, html)`. It is a hand-written tolerant reader and not `html5ever`: the output is only words and run properties, so nothing of the markup, a script, a style sheet, an attribute or an unknown element can survive, which is the sanitising; a full HTML5 tree builder would be a large dependency to arrive at the same few facts. It reads what Chrome writes (a computed style on every span), Google Docs (a `<b style="font-weight:normal">` round the whole paste, which a style that says `normal` takes back), Word (conditional comments, `<o:p>`, `mso-` styles) and the `<!--StartFragment-->` markers, and it decodes the named references writing uses and any numeric one. It is bounded: more than 2 MB of HTML is refused (the window pastes plain words), nesting past 256 levels is read as flat, and an unfinished tag is dropped.

What is kept: bold, italic, underline, strike-through, a link (only an address `clean_href` accepts), a colour, a size and a typeface. A typeface is kept only if the book can draw in it (installed, bundled or kept in the book), the first such name of a CSS list; generic names are not typefaces. Near-black and near-white colours are the ink and paper of the page the words came from and are not kept; transparent and system colours are none. Only `px` and `pt` sizes are read (relative sizes have nothing to be relative to). What most of the words share, their size and typeface, is left off (as the Word and OpenDocument importers do for the body size), so pasted words take the look of the frame they go into and what differs inside the paste (a larger heading, a word in another face) is kept. A link drops the blue and the underline its page gave it, because the page marks a link itself (D-66).

Structure: a block element, a `<br>`, a list item or a table row ends a paragraph; empty paragraphs are dropped, as the book spaces paragraphs and does not keep blank ones; a list item begins with a dash or its number; preformatted lines keep their spaces. Tables come in as a paragraph a row, with a note.

In the on-page editor the paste handler decides in this order: a clipboard Folio filled (`application/x-folio-text+json`) pastes its own paragraphs; with Ctrl+Shift+V just before it, or with no HTML on the clipboard, the plain words are pasted (and set with smart punctuation as typed words are, D-57); otherwise the HTML goes to `paste_html` and the paragraphs it answers are inserted as one `EditText` with `Insert::Rich` and a step of its own, with no smart punctuation, since the words were punctuated where they came from. The read is queued behind the edits before it, and the selection is taken when it is the paste's turn, so a paste cannot land on a stale caret. If Rust refuses the HTML (too large) or finds no words in it, the plain words are pasted instead, so a paste is never lost. Ctrl+Shift+V is noted on key down and the paste event that follows it ignores the clipboard's formatting; the browser's own plain-paste hint is not relied on, because what a webview puts in `clipboardData` for it differs.

Not built: headings becoming a paragraph style, super and subscript, small caps, highlight (`background-color`) and pasted pictures (the clipboard layers' concern).

## The on-page editor keeps its frame selected, stays open, and offers its words to the app

Words selected in the on-page editor could not be styled from the ribbon. The stage let go of the selection on a press anywhere but the page's SVG or a text area, and the on-page editor draws its caret and selection in a box of its own over the page, so a press in the words deselected the frame; every control that needs a selected frame (Bold, Font, Text colour, the Paragraph group) went unavailable and a colour chosen did nothing. A press in the editor's box (`[data-text-surface]`) now keeps the selection.

The editor's blur also no longer relies on `relatedTarget`: WebKitGTK leaves it empty for some presses, so the press that caused the blur says whether it was on the ribbon, a list, a menu or the find bar, and a blur because the window lost the focus keeps the editor open.

The editor also offers the words it holds to the rest of the app (`text/openEditor.ts`): copy, cut, paste (or paste as plain words) and focus, through the same handlers as the keys. A copy or paste asks the webview for the event with `document.execCommand`. WebKitGTK sends the copy event and fills the clipboard from it (though it answers `false`), but sends a paste event only to a page given clipboard access, so the main window is built with `enable_clipboard_access` (the page is Folio's own; no other window has it). Where no event comes, the async clipboard API is used, with a wait so a webview that never answers is given up on, and last the words copied in Folio (`text/systemWords.ts`). The clipboard plugin was tried as the fallback and dropped: on GNOME under Wayland it could not reach a clipboard at all.

## The Properties panel's Paragraph fields keep the editor open

The paragraph fields act on the paragraphs under the editor's caret, but taking the focus to one ended the editing (the editor closed on any blur outside the ribbon, and gave the focus to the page, out of the field), so the change went to every paragraph of the frame and typing afterwards went nowhere. Controls that act on the words being edited now say so with `data-keeps-editor`; the editor stays open while one has the focus, Enter or Escape in a field and a choice of line spacing give the words the focus back, and the editor ends on a press or a focus anywhere else while it does not have the focus itself.

## D-69 · A join keeps the first paragraph's look, unless the first is blank

Backspace at the start of a paragraph, Delete at the end of one, or deleting a stretch across paragraphs joins them, and the joined paragraph has one style and one look. It keeps the first paragraph's, as a word processor's backspace does — unless the first paragraph has no words at all. A blank line is something being taken away, not the paragraph the words belong to: Enter gives a new line the look of the one it was typed in, so a blank line usually carries the look of the paragraph above it, and Delete in it (or Backspace at the start of the paragraph after it) used to hand that look to the paragraph below, changing its spacing. The rule is in `folio_model::replace_range`, and a randomised test (`crates/folio-model/tests/edit_fuzz.rs`) checks it against a plain model of the words over thousands of sequences of typing, Enter, Backspace and Delete on paragraphs with different looks: the words, the number of paragraphs and every untouched paragraph's look come out as the model says, through a frame's own words as well as a story's.

## D-70 · Vertical alignment is a frame override that the layout applies

Words could only sit at the top of a text box (and in the middle of a shape). `StyleOverrides` gains `valign` (top, middle or bottom), set with the `OverrideStyle` intent like the box's size and font, so it needs no intent of its own and old books read as before (absent is the box's usual place). The layout applies it after the lines are placed, moving them down by that share of the room left under the last line; everything that reads the layout — the page, the on-page editor's caret and selection, PDF and fixed-layout EPUB — follows without knowing about it. A frame of a story is placed on its own with the lines it holds, the simplest rule that is right for a story's last frame and does nothing to a full one; flowing the story again for the move is not needed, since moving lines down within their own frame never changes what fits. A frame locked to the baseline grid stays at the top, so its lines stay on the grid. Table cells are left for later.

## D-76 · One two-tab colour picker, with black, custom colours and per-user recents

Colour controls were a drop-down of nine fixed colours with no pure black and no custom colour, and the Inspector had its own grid and hex box. They are now one component, `ColourPicker` in `packages/chrome` (no domain imports; data and labels come in as props), in a fixed-width popover: **Swatches** (from style with Reset, book swatches with ink, pinned black and white, theme colours, recents) and **Custom** (square, hue, hex, RGB in Expert, eyedropper where it exists, contrast against the page). Folio wires data in `apps/folio/src/colour/`; the ribbon gets a generic `colour` control kind, and panels and dialogs use `ColourField`.

The popover is a fixed 340 px, set by a token, because the first design let its width follow the status line's text. Nothing inside sizes to its content. It carries `data-keeps-editor` so choosing a colour does not end the text editing, and portals into a modal `<dialog>` when opened from one. Colour maths (hex parsing, HSV, WCAG contrast, plain-inverse ink) is shared pure code with tests.

Recents are a per-user setting (`recentColours`, up to eight `#rrggbb`, newest first) because a colour you used is about you, not the book; they go through the settings plugin and never browser storage. A swatch of the book is recorded as the colour it shows as.

CMYK sliders were left out of Custom: ink is part of a named swatch (`SetSwatch`), and a slider on a plain colour would have to invent a name. Ink is shown wherever a swatch has it, and the sidebar's Swatches tab remains where ink is made. Highlight has no run field in the model, so its ribbon control stays unavailable until one exists.

## D-71 · Folio prepares the pictures of a PDF itself

The PDF writer used to pass every picture of the book to the library untouched, so a 2400 px painting in a 6 inch frame sat in the file at 400 ppi and a 58 MB book made a 61 MB Sharing PDF. Folio now prepares each picture: it works out the largest place the picture is drawn on any page (backgrounds too), reduces it to the target's pixels per inch for that place when it has more than one and a half times as many, writes photographs as JPEG, keeps flat art, anything with transparency and anything the person asked to keep lossless as pixels, writes grey pictures in grey, brings a picture in another RGB profile into sRGB, and passes a JPEG that is already small enough through byte for byte. A picture used twice is one object in the file, sized for its larger place. The Sharing PDF's usual is 150 ppi at JPEG quality 80; every file for a press keeps 300 ppi at quality 90 and reduces only a picture above 450 ppi. The book's own copy of each picture is never changed.

## D-72 · Fonts stay subset and transparency stays live in every PDF

Full font embedding and transparency flattening are not offered for any PDF. The PDF writer (`krilla`) only embeds subsets of the glyphs a book uses, KDP accepts embedded subsets, and PDF/X-4 allows live transparency; flattening belongs with PDF/X-1a (D-42). The paperback row of `spec/05-export.md` is corrected to say so, with a ⚠ to check against KDP's help pages before a release.

## D-73 · Export settings: built-in, then your defaults, then the book's, then this export's

A person's PDF choices live in four layers, each of which may leave any choice unset: Folio's built-in settings for each kind of file (Sharing, KDP paperback, print shop), the person's own defaults (kept in settings), the book's own (kept in the book, so a collaborator's export matches), and the choices of one export. `folio_export::prefs::resolve` is the one place they are combined: the highest layer that made a choice wins. Each target then locks what its destination requires, putting a value right instead of refusing it and saying so ("Changed for KDP: pictures kept at 300 ppi"). Rust does the combining: the window reads the person's defaults from settings and passes them in with the request, since plugins never call each other (D-27). The old paperback colour choice (`ExportColour`) stays for agents and sits below this export's own choices.

## D-74 · A Sharing or print-shop PDF says it was made by Folio, a KDP file does not

A person who opens a Folio PDF's properties, or a print shop that checks the information of a PDF/X file, expects to see what made it. Folio writes `Creator` (`Folio`), `Producer` (`Folio <version> (krilla)`) and `CreationDate` (the time of the export, never a fixed value) into the information, and the same in the XMP, for the Sharing PDF and the print-shop PDF; the PDF/X-4 step, which reopens the file with `lopdf` and rewrites the XMP, takes the same strings instead of a fixed "Folio" so the two never disagree. The KDP interior and cover keep nothing but the title and author (D-33 and the paperback row of spec 05, ⚠ unverified against KDP's help pages), so they are left out until those pages are checked; it is one condition (`Application::is_written_for`) to revisit. `folio-export` stays free of the app: the caller passes an `Application` through `PdfOptions` (the engine builds it from the host's version), and a caller that passes none gets the old PDF/X producer, `Folio`, and no creator. Tests assert that the strings and a date are present but never the date's value, so they stay deterministic without a clock to inject.

## D-77 · Dialogs with a form or long content are their own native windows, modal where the platform allows, with an in-page blocker as the fallback

The Export dialog, the forms, the previews and the long reports were `<dialog>` elements over the page. They cannot be larger than the window, cannot be moved aside to look at the book, and make a small window feel cramped. Each now opens as a window of its own through the `window-dialogs` plugin, which knows nothing of Folio: `open_dialog(label, spec, payload)` builds a frameless child window of the asker, the dialog reads its payload with `dialog_request` as it starts (no race with it arriving), and `finish_dialog(result)` sends the result to the opener and closes. A window closed any other way sends a cancellation, once. Folio's own `open_dialog` command turns a `DialogKind` into the spec (title, size, whether it can be resized) and the size it was left at.

Tauri has no modal flag, so the plugin uses what each platform has. On Windows the dialog is owned by its opener, which is disabled while the dialog is open and enabled and focused before the dialog is destroyed (otherwise Windows activates another application). On Linux the dialog is a transient and a GTK modal. GNOME attaches it to the parent; KWin and wlroots treat a GTK 3 transient as an ordinary window, because GTK 3 has no `xdg_dialog_v1`, so the opener's page also covers itself with a blocker while a dialog is open, which takes the pointer and brings the dialog forward when pressed. The mock runtime cannot parent or block a window, so platform behaviour is checked by hand.

A dialog form is written once and drawn in a `DialogSurface`, which is the shared in-page `Dialog` in the page and the whole window (with a close-only title bar) in a dialog window, so there is one form and two thin hosts. A dialog window watches one book by id (the books store's `pinned` role) rather than following the main window, and its changes go through Rust, so the main window updates by itself (D-02). Windows are on by default, and Preferences → Interface → Open dialogs in their own windows turns them off for a desktop that handles them badly. The in-page hosts are kept for that, and because modality has been checked by hand on only some platforms; they can go once the manual checklist (`docs/dialog-windows-checklist.md`) has passed on each. The link dialog stays in the page until the editor's selection and focus layers have landed.

## D-78 · Questions with two or three answers use the system's message dialog

Closing a book with changes and finding recovered work on a book each ask a three-answer question that was drawn as an in-page dialog. With dialogs as windows (D-77) these use the platform's own message dialog, through `tauri-plugin-dialog`'s `message` with custom Yes/No/Cancel labels, behind a `Questions` interface (`dialogs/questions.ts`) so tests stand in for it. It is a real modal window, appears at once with no webview to start, is parented to the window that asked, and follows the platform's look and keyboard rules. The cost is that the destructive answer is no longer drawn as a danger button; the labels carry the meaning. A dismissed dialog, or a label that does not match an answer, is the last answer (cancel), so nothing is lost by closing it. Dialogs with a form or content to read still use windows of their own.

## D-79 · Dialog windows are modeless or modal transient children, and a modal one is not a GTK modal

Hand-testing D-77 found that dragging a dialog's title bar also dragged the main window. The cause is GNOME's "attach modal dialogs": a GTK modal that is transient for a window is attached to it and moves with it. The dialogs split by pattern. A _modeless transient child_ is a window with its opener as parent (a transient on Linux, owned on Windows) so it stays above the opener and minimises and closes with it, but it is not modal, no blocker or dim is put over the opener, and the opener stays usable: Export, Check book, Cover sheet, Soft proof, Story editor and Spread templates. A _modal transient child_ blocks its opener: Book size, Margins, Book details, Barcode, Page background (its live preview is tied to the main window), Import report, Update and Connect an agent. `DialogSpec.modal` chooses; the plugin skips the block, the `modal` event and the one-modal-per-window rule for a modeless dialog while still setting the parent.

On Linux a modal dialog no longer calls `gtk_window_set_modal`. The opener is made insensitive for as long as the dialog is open, which drops its input without the compositor treating the dialog as an attached modal, so the dialog moves alone. The page blocker stays as the fallback for compositors that ignore the transient.

The frame is the main window's, not a card of its own. A dialog window uses the same `WindowFrame` as every other window, so on Windows the OS draws the shadow and the page draws no margin, and on Linux the D-13 transparent margin and CSS shadow are used; a second, dialog-specific card and shadow inside the window is not drawn. A dialog is never maximisable or minimisable (the builder says so, and the shared `DialogWindowFrame` swallows a double-click on whatever title bar it is given), and its content is a bounded, centred column with the buttons pinned below it, so a dialog that is resized (or was maximised by a window manager) does not leave its content in a corner and its buttons in the far corner.
